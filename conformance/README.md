# Conformance suite — fixture format and result shapes

This file is the contract between the fixtures and any implementation run by `run.py`. The fixtures encode the outcomes the Attedra Specification 0.1.0 states. The result shapes below are this reference's own; the specification fixes what a result must contain, not its field names. A bare rule number, such as (9.2.1), refers to the specification.

## 1. Fixture file

One case per JSON file in `fixtures/`, named `<family>_<nn>_<slug>.json`:

```json
{
  "id": "T05_01_withdrawal_of_latest_value",
  "family": "T05",
  "rules": ["6.7.4", "5.6.1", "12.5"],
  "description": "Withdrawing the latest value leaves no current value; the older value is not revived.",
  "steps": [ ... ]
}
```

A fixture may carry `"blocked_on_spec": "<issue id>"`. The runner then reports it as BLOCKED, not as passed or failed.

A fixture may carry `"note"`, free text that explains an outcome, for example by quoting the rule that determines it. It may carry `"transition_check": false` only together with a `note` that quotes the rule making the transition check of §8 inapplicable to it; the runner then skips that check for it.

## 2. Steps

Steps run in order against a fresh, empty store. A write step may carry `"expect_error": "<code>"` (§6), in which case the write must fail with that code and leave the store unchanged. A write step without it must succeed. Any step may carry `expect`, a pattern (§3) matched against the step's result; a step with `expect_error` has no result to match.

| `op` | Fields | Meaning |
|---|---|---|
| `item` | `id`, `kind`, optional `label`, optional `definition`, or `definition_json` in place of `definition` | Create Item (spec 8.1.5). `definition_json` is raw JSON text, parsed like `values_json` (§6), so that a duplicate key in a definition can be tested (5.1.1). |
| `items` | `items`: list of the above | Create several Items, in order. |
| `assert` | `item`, `context`, `source`, `values` or `values_json` (§6), optional `recorded_at`, `recorded_by` | Write an Assertion: insert or identical replay (8.1). This includes every act: the operation is chosen by `values["@action"]`. Disconnect and reconnect acts also update the targeted Connection (8.6). |
| `connect` | `from`, `to`, `at` (instant) | Create Connection (8.6.1). |
| `plan_removal` | `target` (a compact Assertion reference or an Item id, §4), optional `as` (a name to bind the plan identifier, when a plan is returned) | Plan removal (8.5.3). |
| `confirm_removal` | `plan` (`"$name"`) | Confirm removal (8.5.4). |
| `cancel_removal` | `plan` (`"$name"`) | Cancel a plan (8.5.4). |
| `read` | `read` (a name from §5), `args`, `expect` | Run a read and match its result against `expect`. |
| `retire_interpretation` | `name` (a fixture interpretation, §5 *Interpretations*) | From this step to the end of the fixture, the reference does not have the named interpretation. Records written before the step stay as written. It stands for records made by an implementation that had the interpretation, read by one that does not (7.3.8, 7.6.14), now that a normalization naming an interpretation the reference does not have is rejected (10.2.9). |

**Write results.** The write ops return:

- `item`: `{"status": "created" | "exists", "id"}`. `exists` is an identical re-creation (the same `kind`, `label` and `definition`), a successful no-op (8.1.5). Re-creating an existing id with different content fails `occupied` (§6). `items` returns a list of these, one per Item, in order.
- `assert`: `{"status": "inserted" | "replayed", "ref": <compact reference>, "generated": [<compact references>], "transition_acts": [<compact references>]}`. `replayed` is an identical replay (8.1). `generated` lists the Assertions that story maintenance recorded in the same operation (§7), in the order recorded. `transition_acts` lists the begin acts, end acts and `revise` reconciliations recorded in the same operation (§7, *Recorded transitions*), in the order recorded; `generated` never lists them. Both are empty for a replay.
- `connect`: `{"status": "created" | "exists"}`. `exists` is the 2.2.1 no-op, which never reconnects. When a created Connection changes which normalizations apply to a subject (7.3.8), the result also carries `generated` and `transition_acts`, as for `assert` (§7, *Normalizations*).
- `plan_removal`: one of
  - `{"status": "planned", "plan": "<id>"}`, when the target has no dependents;
  - `{"status": "refused", "dependents": [<refs>]}`, when it has dependents (8.5.3);
  - `{"status": "refused", "reason": "not_found", "dependents": []}`, when the target is not recorded;
  - `{"status": "refused", "reason": "interpretation_unavailable", "interpretation": <name>, "dependents": [<refs>]}`, when the impact test examines a unit evaluated under an interpretation the reference does not have (§5, *Unavailable interpretations*; 8.5.2, 10.3). `dependents` lists the dependents found otherwise;
  - `{"status": "refused", "dependents": [<refs>], "extension": "@x-fixture-refs"}`, when the target carries the declared extension (§5, *Declared extension*), or when the target is an Item and any record in the store carries it (10.4.4). `dependents` then lists any other dependents, and is empty when there are none.
- `confirm_removal`: `{"status": "removed"}`.
- `cancel_removal`: `{"status": "cancelled"}`.
- `retire_interpretation`: `{"status": "retired"}`.

**Dependents.** `dependents` is a set, listed sorted by compact form (§4). For 8.5.2(a) and (b) it lists the referencing record. For (c) it lists the record whose derived result would change: an Assertion whose occurrence time or distribution coverage changes, an expectation whose standing changes, or a story Item whose interval, standing or ending changes, including a story whose only detection is the target. For (d) it lists the Assertions, Items and Connections (`from->to`) that use or reference the Item. A begin act, end act or `revise` is never removable (8.5.2): its plan is refused, and `dependents` lists its unit's record under (c) (the story Item, or the expectation's compact reference without a selector), together with the records that reference it. A record that a begin act, an end act or a `revise` cites in `@period`, or a `revise` in `@basis`, lists that act among its dependents under (a) or (b).

**Plan lifecycle.** A plan identifier is valid only in the session that issued it. Confirming or cancelling a plan ends it. A confirm revalidates the target and every record the impact test examined (8.5.2(c)); if any of them changed, the confirm fails `plan_stale` and the target is untouched. A confirm or cancel of a plan that the session did not issue, or has already confirmed or cancelled, fails `plan_unknown`. A step's `plan` is `"$name"`, a name bound by `as`; a `plan` that names no bound plan is passed as written, so that a fixture can present an identifier no session issued.

Instants are strings in spec 4.2.1 form. Items, contexts and sources are always created explicitly before they are referenced, except in a write step with `"expect_error": "10.2.2"`, whose Assertion coordinates or `connect` endpoints may name an Item that does not exist (2.3.2, 10.2.2).

**Context Items** carry `definition: {"@context": {...}}`:

- event: `{"role": "event", "at": "2026-06-02T10:00-07:00"}`
- milestone: `{"role": "milestone", "schedule": {"@ref": "item", "id": "arch-schedule"}, "stage": "50% CD", "ordinal": 50}`. Its publication is an `assert` of `(M, M, <log>)` with `{"@published": "<instant>", "@distribution": [...]}`.
- phase: `{"role": "phase", "schedule": {...}, "starts": <milestone ref or instant>, "ends": <milestone ref or instant>}`
- expectation: `{"role": "expectation", "timing": {"type": "by", "instant": "2026-06-27-07:00"}, "fresh": true}`. Timing is `{"type": "at", "milestone": ref}`, `{"type": "during", "phase": ref}`, `{"type": "by", "instant": "..."}` or `{"type": "by", "milestone": ref}`, or `{"type": "any"}`, with an optional `preferred_issuance`.

## 3. Matching

`expect` is matched as a subset pattern against the result:

- Objects: every key in the pattern must be present in the result and match. Keys absent from the pattern are not checked.
- Lists: matched element by element, in order, and must have equal length. The exception is a pattern list whose first element is the string `"~unordered"`: the remaining elements are matched as a multiset, in any order, still with equal length.
- `"~absent"` as a value requires the key to be missing from the result.
- `"~any"` matches any present value.
- Scalars: strict JSON equality. Numbers compare by decimal value, so `1` matches `1.0`.

## 4. References in results and steps

- An Assertion reference is written as the compact string `"item|context|source"`, for example `"door-101|arch-50cd|a-601"`.
- A selector is appended as `"#property"` (`"door-101|e1|a-601#finish"`) or as `"^support:<expectation ref>"` (with an optional `"#property"` after it).
- An Item is its id string. A Connection is `"from->to"`.
- In step `values`, references are always full spec reference objects (`{"@ref": ...}`). The compact forms are used in results, in `expect` patterns, in the `target` of `plan_removal`, and in read `args`: `ref` in `exact` and `expectation`, and `from_assertion` and `to_assertion` in `changes`, are compact references, and Item arguments (`subject`, `source`, `party`, `story`, `item`, `participant`, a scope, a milestone cutoff) are ids.

## 5. Reads and result shapes

**Frame.** Every read takes a `frame` in `args`: `{"scope": <scope item id or list of ids>, "cutoff": <instant | milestone id | "now">, "perspective": "record" | <participant id>, "interpretation": null | <name> | "literal"}`. Omitted keys default to scope = every Item in the store (allowed only in fixtures), cutoff `"now"`, perspective `"record"` and interpretation `null`. An interpretation of `null` names none: each comparison then uses the interpretation that applies to it (4.6.1, 7.3.8). That is the interpretation in force for its subject at its time, which is literal comparison until a normalization applies, except that an expectation is evaluated under its own interpretation (7.6.13), whatever normalizations apply, and two expectations are compared under theirs (7.2.4). A name computes every comparison under that interpretation at every instant. `"literal"` requests literal comparison: it computes every comparison literally at every instant, whatever normalizations apply, and is treated wherever this contract speaks of a named interpretation as naming literal comparison (4.6.1). No fixture interpretation is named `literal`. Only the resolved frame reports such a request as `"literal"`; every other `interpretation` member of a result, and of a recorded `@frame` (5.5.5), reports literal comparison as `null`, under this frame as under any other. `exact` and `item` return the record as recorded, whatever the frame.

- *Resolved frame.* Every result carries `"frame"`, the resolved frame: `{"scope", "cutoff", "perspective", "interpretation", "interpretation_version"}`. `scope` echoes the input, or is `null` when it was omitted. `cutoff` is the resolved instant. For a `"now"` or milestone cutoff, `cutoff_input` also echoes the input (`"now"` or the milestone id); it is absent for an instant cutoff. `perspective` is `"record"` or the participant id. When the frame names an interpretation, `interpretation` and `interpretation_version` are that name and `"1"` for every fixture interpretation below, and `"literal"` and `null` for a frame that requests literal comparison. When it names none, they are the interpretation in force for the scope at the cutoff (4.6.1): the name and version that the normalization in force names, or `null` and `null` for literal comparison. The resolved frame then also carries `normalization`: the compact reference of the normalization that put that interpretation in force, or `null` when none applies. Where the interpretation in force is ambiguous (7.3.8), `interpretation` and `interpretation_version` are `null` and `normalization` is `{"ambiguous": [refs]}`, listing the normalizations concerned, sorted. `normalization` is absent when the frame names an interpretation or requests literal comparison. For a scope given as an Item id, the interpretation in force is that of the scope Item; for a list, or an omitted scope, it is that of every listed Item (every Item in the store), ambiguous when they differ. Fixtures that pin a resolved frame after recording a normalization name a scope Item. Other reads in such fixtures may omit the scope, which the reference then resolves by loading every normalization and Connection in the store.
- *Scope.* A scope given as an Item id has as members that Item itself and the Items reached from it by following Connections forward, transitively, using the Connections active at the cutoff (2.1.5). Expectations and stories about the scope Item itself are therefore in scope, with or without a Connection cycle. A scope given as a list of ids names its members directly.
- *Now.* `"now"` resolves once per read, to the evaluation instant, at a precision no coarser than the second (4.6.1). The reference resolves it to the wall clock at second precision in UTC, written `YYYY-MM-DDTHH:MM:SS+00:00`.
- *Perspective.* A participant perspective restricts which statements and acts count; it does not restrict chronology. A milestone's publication instant, and with it the occurrence time of the Assertions at that milestone, a milestone deadline (6.2.4) and a milestone cutoff, are the same in every perspective. The publication Assertion's own property values count for a participant only once it was distributed to them (4.4.2, 4.6.1).
- *Instants in results* (`cutoff`, `qualifying_moment`, `deadline`, a story's `interval` and `ending.at`, a `<transition>`'s `at`, a distribution's `at`, `by_party` times, adjacency `history` `from` and `to`, Connection properties, `event_time.cutoff`) are returned as written in the record or argument that supplies them, at the same precision and offset, never normalized (4.2.1). A resolved `"now"` is written as above.
- *Presentation order.* Where a list below is "in presentation order", its records are ordered by time (an act's effective time when the act may carry `@effective` (8.4.1), otherwise the record's occurrence time; an earlier interval start first, then an earlier end), then by the ordinal of a milestone context, then by item, context and source id. Records with no time come last. This order is presentation only, never sequence evidence (4.5.2).

**Interpretations.** The reference provides these named interpretations, for fixtures only, each at version `"1"`:

- `"fixture-fire-rating"`: `"90 min"`, `"1.5 h"` and `90` are equal.
- `"fixture-set:<property>"`: that property's list values are sets (5.5.3).
- `"fixture-accept-empty:<property>"`: an explicit empty value (`null`) is an acceptable answer to an information request (`{"@ask": true}`) on that property (6.4.4). It changes no equality: `null` still does not meet a required non-empty value, and every other comparison is literal.

Each covers every value: outside the equivalences it declares, it compares literally, so the reference never reports a value its interpretation does not cover (5.5.4). Any other name is unavailable, and so is a fixture interpretation after a `retire_interpretation` step that names it (§2).

**Normalizations.** A normalization (7.3.8) is an `assert` of an act with `"@action": "reinterpret"`, `"@targets": [{"@ref": "item", "id": <scope Item>}]` and `"@interpretation": {"name": <name>, "version": <version>}`, or `"@interpretation": null` for literal comparison, with `@basis`, `@party`, `@issuance` and `@effective` as for any act. A normalization whose `@interpretation` names an interpretation the reference does not have fails `10.2.9`, and so does a `replace` correction whose `@corrected` values are such a normalization (7.3.8, §6). An identical write of either, already recorded before a `retire_interpretation` step, is a replay (8.1.2, 10.2.9). A story's interpretation, and that of an expectation whose context names none, is at each instant the interpretation in force for its subject (7.2.4, 7.6.13); a detection's `@frame` never sets it, and a detection whose `@frame` names another interpretation is accepted. An expectation whose context names an interpretation keeps it at every instant, and every read whose frame names none reads the expectation under it (7.6.13, 7.6.14). A conflict story between two expectations, and a `conflicts` read of them under a frame naming none, compares each side under its own interpretation: equal when equal under both, unequal when unequal under both, and ambiguous otherwise (7.2.4). Where a comparison's values are unequal literally and equal only under an interpretation that a normalization put in force, the result carries `matched_by`: the compact reference of that normalization (5.5.4). It is given where stated below: on a `fulfilled` `<standing>`, an `unchanged` changes `<transition>`, a `conflicts` `matched` entry, a story's `<ending>` and `standing`, and a `<transition>` of a period. Where several normalizations put that interpretation in force, one per normalized scope Item of the subject or tied ones of one scope Item (7.3.8), `matched_by`, a normalization ending's `record`, and the `normalization` of a resolved frame or a `story` read are the list of their compact references, ordered as in 7.6.6. In a participant perspective, a normalization that carries `@issuance` counts once that issuance has been distributed to the participant, and then applies from its effective time (4.6.1, 7.3.8).

**Unavailable interpretations.** A unit is evaluated under an unavailable interpretation when, at any instant, its own interpretation is one the reference does not have (7.6.14): the interpretation in force for a story's subject, put in force by a normalization written before a `retire_interpretation` step that names it (§2), or an expectation's interpretation, named by its context's `interpretation`, including that of an expectation side of a conflict story (7.2.4). One rule covers it:

- *Read as recorded.* Its begin and end acts are read as recorded by every read that evaluates the unit under its own interpretation, including one whose frame names that interpretation. They are never revised on that account, and `transition_check` lists them as `unverified`. A unit first recorded in that state gets one begin act whose `@period` is `{"limitation": "interpretation_unavailable", "records": [], "interpretation": <name>}`, and reads list it among their limitations. Maintenance records for it no continuation, related story or reconciliation whose need depends on the interpretation (7.2.8).
- *Computed results are limitations.* A result that would have to be computed under the interpretation is `{"limitation": "interpretation_unavailable", "interpretation": <name>}` in its place, never a literal substitute. In a `story` read, the `disagreement` dimension and `match_under_read_interpretation` take that object as their value; the other members are read as recorded. A `what_remains` entry keeps its list and carries the object as its `disagreement`. In a participant perspective, a `story` read of the unit returns the object in place of its result, and listing reads list the unit among their limitations. A computed `expectation` read under the interpretation, and a `conflicts` or `changes` read whose comparison needs it, give the limitation as stated under *Limitations*. A `plan_removal` whose impact test examines such a unit is refused, with `"reason": "interpretation_unavailable"` beside its `dependents` (8.5.2, 10.3).

**Ending policies.** The reference implements one ending policy (7.7), for fixtures only: `"fixture-change-closes-with-directive"`, version `"1"`. A unit is governed by it from the start when its first detection's `@frame` carries `"policy": "fixture-change-closes-with-directive", "policy_version": "1"`, or when its expectation context's `@context` carries `"policy": {"name": "fixture-change-closes-with-directive", "version": "1"}`. It is governed by it from the effective time of an `adopt_policy` naming it, which may carry `@effective` (8.4.1), until a later `adopt_policy` takes effect (7.7.2, 7.7.3). The reference records and revises its end acts as maintenance (§7) for every period it governs at some instant, each with `"policy": {"name": "fixture-change-closes-with-directive", "version": "1"}` in `@period`. Each end act gives the policy's own ending of the period, as below, whenever the policy governs; when the policy begins to govern a period after that ending, the period ends at the start of its governance (7.7.3), which reads report and the act does not change.

- *Approval.* A change story's period that an approval (`no_change`) ends under the baseline ends under the policy at the same instant, with cause `review` and the review as its record.
- *Directive.* A period that a directive (`change_required`) ends under the baseline ends under the policy once every expectation property that the directive covers through `@establishes` or `@reaffirms` has ended under the baseline, by fulfillment or by withdrawal. For each property, the ending counted is that of its period in force at the directive's effective time. The policy's period ends at the latest of those endings, or at the directive's effective time if that is later. Its cause is `directive_closed`, and its record is the ending record of the property that ended last; where several ended last at one instant, it is the list of all their ending records (7.6.6). Where the latest of those endings is unordered, the content is ambiguous (7.6.6).
- *Directive withdrawn first.* When the directive's withdrawal takes effect before that, or at the instant of the last of those endings (as when the directive was a property's only support), the period ends under the policy at the withdrawal's effective time, with cause `withdrawal` and the withdrawal as its record. The baseline's next period begins at the same instant, unless another review of the story remains in effect then (7.6.2).
- *Other units.* Conflict stories and expectation properties governed by the policy end as under the baseline: for each baseline end act, an end act naming the policy is recorded with the same content.
- *Normalization endings.* A change story's period that a normalization ends under the baseline (7.2.7, 7.6.2), including a period of no length that begins at a review's withdrawal, ends under the policy in the same way, with the same content.

*Tied `adopt_policy` acts.* Where `adopt_policy` acts of one unit are tied or unordered, with no `@after` evidence ordering them, and name different policies, the policy governing the unit from then is ambiguous (7.7.2). Where they name the same policy, that policy governs. An ambiguous policy is reported, wherever a result has a `policy` member, as `{"ambiguous": [<candidate>, ...], "records": [refs]}`. Each candidate is `null` or `{"name", "version"}`, once per distinct policy, in the order of the tied acts' compact references, and `records` lists the tied acts, sorted. The reference records the fixture policy's end acts for every period it governs, or is a candidate to govern, at some instant. A result that depends on the governing policy is evaluated under each candidate, and is the common result where all candidates agree. Otherwise a period's `policy_end`, and a story's `ending`, is `{"ambiguous": [<candidate>, ...], "records": [refs]}`, each candidate being that result under one policy (`null` where the period has not ended under it), with the tied acts as `records`. `standing.open` then reads `ambiguous` where the candidates differ on whether the period has ended, and listing reads place the unit among their ambiguous entries.

Any other policy name is not implemented. The reference still reads the end acts recorded for it (7.7.5), and `transition_check` lists them as `unverified`. The fixture policy reads each covered property's baseline ending from that property's applicable recorded baseline end act. It therefore needs no interpretation, including where a covered property's interpretation is unavailable (*Unavailable interpretations*, above).

**Limitations.** A read that cannot be evaluated as asked returns `{"limitation": "<code>", ...members, "frame": ...}` in place of its result (9.6.1, 10.3). Some results instead carry a limitation in place of one entry, as stated for `source_position`, `resolved_view`, `open_work`, `expectations_about`, `open_stories`, `pending_review` and `what_remains`. A begin or end act whose content is a limitation (7.6.6) uses the same codes. Codes and their members:

- `relocated_reference`: `correction`, `record` (the record holding a reference that a relocation left dangling), and, in `source_position`, `original` (the relocated Assertion) (8.3.7).
- `relocated`: `correction`, `replacement`. An `expectation` read of an expectation that a correction relocated (8.3.7).
- `no_occurrence_time`: `records`, the statements concerned, which have no occurrence time (4.2.4): at a planned milestone, or at a context whose corrected definition has no `@context`.
- `interpretation_unavailable`: `interpretation`, the name, and `literal`, the result of the same read under literal comparison, labelled as literal. A `conflicts` or `changes` read whose comparison needs an unavailable interpretation, named by its frame, in force for its subject, or, for a pair of expectations, named by one's context (7.2.4), returns this (5.5.4). So does an `expectation` or `expectations_about` read that must compute an expectation under an unavailable interpretation, and `open_work` lists such an expectation among its limitations. An expectation read under its own interpretation is read as recorded, whether or not the reference has that interpretation (*Unavailable interpretations*, above). A unit's own entry carries `{"limitation": "interpretation_unavailable", "interpretation"}` without `literal`.
- `planned_milestone`, `competing_publication_instants`: `milestone`. A milestone cutoff that cannot be resolved (4.6.1).
- `cutoff_unresolvable`: `cutoff`. A cutoff that is not an instant, `"now"` or a milestone.
- `reversed_comparison`: none. A `changes` read whose first side is after its second (5.6.2).
- `unordered_comparison`: none. A `changes` read whose two cutoffs are unordered (4.2.5, 5.6.2).
- For a `story` read of an Item whose detections do not form one conflict or change story, the code names the defect: `conflict_story_sides_not_two`, `conflict_story_mixes_statement_and_expectation` or `story_unresolvable`.

**Side reports.** A result may also carry the following members. Each is absent when it would be empty, except `excluded`. Patterns that do not name them are unaffected (§3).

- `excluded`: on every result evaluated in a participant perspective, the compact references of the records the perspective excluded, sorted (4.6.1, 9.7.2).
- `unsupported`: the compact references, sorted, of the extension records the read encountered (10.4.2, 9.6.1). These are Assertions with an undefined `@action`, or carrying an undefined `@` member (10.4.1), that are about the read's subjects or that target records about them. For `story`, they are those that target the story or its detections. A read's subjects are the Items named in its arguments, the subject of the expectation it reads, or, for a scoped read, the scope's members.
- `discrepancies`: `[{"discrepancy": "ordinal_order_disagrees_with_publication", "milestones": [<ids, sorted>]}]`, when the read's evaluation orders milestones of one schedule whose ordinal order disagrees with their publication instants (4.3.4).
- `competing_publications`: on `source_position`, `[{"record": ref, "competing": [refs]}]` for each of the source's statements about the subject at a milestone with competing publication instants, listing the competing publication Assertions (4.4.1).
- `ambiguous`: on `conflicts`, the pairs whose comparison depends on an unspecified order (see `conflicts`).

**`exact`.** `ref` is a compact Assertion reference, a Connection `"from->to"` or an Item id. A `not_found` result carries only `status` (and `frame`).

- *Assertion.* `values` are as recorded. `corrections` lists every correction in the corrected account that targets the record, in presentation order. `applicable_correction` is the one that applies (8.3.4); where corrections are tied, `corrections_ambiguous` lists the tied ones in its place. Both are absent when no correction targets the record. `corrected_values` carries the values every other read uses, present when an applicable correction changes them. `withdrawals` lists the withdrawals that target the record, in presentation order. `dependents` lists the records that reference it exactly (2.4.5), sorted.
- *Act.* For a detection, review or reconciliation, the result also carries `basis_corrections`: `[{"record": ref, "corrections": [refs]}]`, one entry for each Assertion in its `@basis` that a correction now targets (8.3.6), absent when there is none. It also carries `event_time`: `{"cutoff": the act's @frame cutoff, "records": [refs], "differs": bool}`. `records` are the applicable Assertions of the question the act recorded, in the current event-time account at that cutoff: for a conflict story, its two sides; for a change story, the revision's prior and new Assertions. `differs` says whether they differ from the ones the act cited (9.8.1). `event_time` is absent for a `revise` (7.6.10) and for an `adopt_policy` that targets an expectation (7.7.3). A begin or end act, and a normalization, is not a detection, review or reconciliation, and carries neither member.
- *Connection.* The result is `{"status", "properties": {"connected_at", "disconnected", "disconnected_at"?, "disconnect_reason"?, "reconnected_at"?}, "derived": {...}, "corrections": [refs]}` (2.2.4). `properties` is the stored materialization, which equals the derivation from the acts (8.6.6). `derived` is that derivation, returned by the reference as a self-check.
- *Item.* The result is that of `item`.

**`item`.** The exact read of an Item: `kind`, `label` and `definition` are as recorded. When a correction applies, `corrected` carries the corrected `kind`, `label` and `definition` that every other read uses (8.3.8); it is absent otherwise.

**`source_position`.** Listed are the properties carried by any statement of that source about the subject (an Assertion that is neither an act nor an expectation, 9.2.2) in the corrected account, at any cutoff, plus any named in `args.properties`. A property first asserted after the cutoff, or only in statements the perspective excludes, is listed as `never_asserted`. A property carried by a statement with no occurrence time has `{"limitation": "no_occurrence_time", "records": [refs]}` in place of its classification, naming those statements; the source's other properties are classified as usual (9.2.2).

A `<classification>` is `{"classification": "never_asserted" | "asserted" | "withdrawn" | "ambiguous", "value": <json>, "origin": ref, "withdrawn_by": ref, "withdrawn_assertion": ref, "candidates": [<classification>]}` (5.6.1). `value` and `origin` are present only when asserted; `withdrawn_by` and `withdrawn_assertion` (the withdrawn Assertion) only when withdrawn; `candidates` only when ambiguous. Each candidate is `{"classification": "asserted", "value", "origin"}`, `{"classification": "withdrawn", "origin": <the withdrawn Assertion>, "withdrawn_by"}` or `{"classification": "never_asserted"}`.

**`resolved_view`.** Properties are those `source_position` would list for any source that has a statement about the subject carrying a property. Under each property there is an entry for every such source, `never_asserted` included. A source whose classification is a limitation has `{"limitation": code, ...members}` in place of its classification.

**`by_party`.** `statements` and `acts` are in presentation order. `details` has one entry per listed record, the statements first and then the acts, each in list order: `occurrence` is the record's occurrence time or `null`; `effective` (the act's effective time or `null`) and `action` are given for acts only.

**`expectation` and `expectations_about`.** `in_force` is true while at least one support covers at least one of the expectation's properties (6.3.1). A `ref` that is not a recorded expectation returns `{"status": "not_found"}`. `expectations_about` lists every expectation about the subject, in force or not, ordered by item, context and source id; an expectation whose standing is a limitation has `{"expectation": ref, "limitation": code, ...members}` as its entry. `policy` is the expectation's ending policy at the cutoff (7.7.2), `null` for the baseline, or the ambiguous form of *Ending policies* above. In the record perspective, when the read evaluates the expectation under its own interpretation (7.6.13), the standings and periods are read from the recorded acts (7.6.14); otherwise they are computed. It does so when the frame names no interpretation, whether or not the expectation's context names one, or when the frame names the interpretation the context names (7.6.14). Any other frame interpretation, `"literal"` included, computes them under that interpretation at every instant.

A `<support>` is `{"support": ref, "covers": [p], "withdrawn_by": [refs]}`. `supports` lists every support whose occurrence time is at or before the cutoff, whatever its coverage, in presentation order, which for supports is effective-time order (8.4.1): each establish or reaffirm act that targets the expectation, and each review of either outcome that lists it in `@establishes` or `@reaffirms` (6.3.1, 7.4.1). `covers` lists, sorted, the properties the support covers at the cutoff; a support whose target, or whose `@establishes` or `@reaffirms` entry, carries a `property` selector covers at most that property (6.3.1). `withdrawn_by` lists the withdrawals that ended its coverage, or voided it before it began, at or before the cutoff (6.3.3, 6.7.2), and is empty when there are none.

`<overall>` is computed from the property standings (6.4.5, 6.6.2). It is `"not_in_force"` when every property is `not_in_force`. Otherwise the properties that read `not_in_force`, which no support has covered, are left out, and it is `"open"` when any remaining property is `outstanding` or `not_yet_due`; otherwise `"fulfilled"` when every remaining property is `fulfilled`; otherwise `"closed"`, every remaining property being `fulfilled` or `withdrawn`. When a property's standing is `ambiguous`, `overall` is computed with each of its candidate standings. It is the common value when all agree and `"ambiguous"` otherwise.

A `<standing>` is `{"standing": "not_in_force" | "fulfilled" | "withdrawn" | "outstanding" | "not_yet_due" | "ambiguous", ...}` (6.6.1, 9.3.1). Every standing carries `timing` and `interpretation`, and the other common members where they apply:

- `timing`: the expectation context's `timing` object, as recorded;
- `interpretation`: the name of the interpretation applied to the property, or `null` (5.5.4): for a `fulfilled` property, the one it was fulfilled under; otherwise the one applied at the cutoff;
- `deadline`: with `by` timing, once the deadline is known, the resolved deadline instant;
- `suggested`: for an information request with a suggestion, the suggested value (6.4.1);
- `unqualified`: where the expectation's source is an eligibility Item (6.1.3), `[{"evidence": ref, "unmet": "no_criteria_in_force" | "missing_producer" | "producer" | "missing_agent" | "agents"}]`. It lists each Assertion about the subject that carries the property but whose source does not qualify, with the unmet criterion (3.3.2): no source had criteria in force at the evidence's occurrence time; the issuance names no `@producer`; its `@producer` is not the named party; the criteria state `agents` and the issuance names no `@agent`; or none of its `@agent` Items is among `agents`. It is absent when empty;
- `source_current`: the obligated source's current `<classification>` of the property. It is absent when the expectation's source is an eligibility Item, which names no single obligated source;
- `periods`: the property's periods (*Periods*, below), `[]` when no support has begun one.

Each standing value also carries its own members:

- `not_in_force`: no support had covered the property at or before the cutoff (6.3.3). `withdrawn_by` lists the withdrawals that ended supports before they took effect, and is empty when there are none. The expectation may be in force through another property while this one reads `not_in_force`.
- `fulfilled`: `timeliness` (`"on_time"` | `"late"` | `"ambiguous"`), `fulfilled_by` (ref, or, where several Assertions at one occurrence time fulfill it, the list of them in the order of 7.6.6; 6.5.1), `qualifying_moment` (instant), `late_by` when late, `matched_by` (ref) when the evidence meets the requirement only under an interpretation that a normalization put in force (6.5.1), and `later` when the property's requirement ended after the qualifying moment and at or before the cutoff (6.6.1). With `at`, `during` or `any` timing, `timeliness` is `"on_time"` (6.5.4).
- `withdrawn`: `withdrawn_by` (refs): for each support that covered the property during its last in-force period, the withdrawal that ended that coverage (6.6.1, 6.7.2).
- `outstanding`: `overdue` (bool).
- `not_yet_due`: `overdue`, always `false` (6.2.1).
- `ambiguous`: `candidates`, `records` (refs: the records whose unspecified order it depends on, 4.5.3, 6.6.1) and, when criteria of different sources disagree, `criteria` (refs: each source's `@eligible` Assertion in force at the evidence's occurrence time, 3.3.2, 9.6.1). Each candidate is a complete `<standing>` for one order and carries the members of its own standing value: `fulfilled_by`, `qualifying_moment` and `timeliness` when fulfilled, `withdrawn_by` when withdrawn or not in force, `overdue` when outstanding or not yet due. The common members are given once, on the ambiguous standing itself.

`late_by` is an ISO 8601 duration: `"P2D"` when the difference is whole days, otherwise `"PT<n>S"`. It is computed between the ends of the deadline's and the evidence's intervals (4.2.5). Each `later` entry is `{"kind": "withdrawal", "record": ref}`, and the records are those `withdrawn_by` would carry for that ending. A withdrawal that leaves another support covering the property is not an ending and is not listed.

**Periods.** A `<period>` is `{"begin": <transition>, "end": <transition> | null, "policy_end": <transition> | null}` (7.6.2). `begin` is the period's begin act. `end` is its baseline end act, or `null` while it has none whose applicable content is not `null`. `policy_end` is present only when a non-baseline policy governs the unit at some instant of the period (7.7.3): it is the end act of the policy governing the unit when the period ends, or `null` while the period has not ended under its governing policies. Its `at` is the instant at which the period ends under them: the later of the act's own `at` and the effective time from which that policy has governed the unit without interruption up to that ending, so it differs from the act's `at` only when the policy began to govern after its own ending held. `policy_end` then also carries `policy`, naming that policy (`null` when the baseline governs the period's ending). Where the policy governing the period's ending is ambiguous, `policy_end` takes the ambiguous form of *Ending policies* above. A `periods` list has one entry for each begin act of the unit whose applicable content is not `null`, ordered by the beginning's `at` (an ambiguous beginning by the earliest of its definite candidates), then by the act's compact reference. It lists the recorded periods whatever the cutoff, since recorded transitions apply at every cutoff (7.6.8); the standing reports what holds at the cutoff.

A `<transition>` is the applicable content of a begin or end act (7.6.6, 7.6.10), with the act: `{"act": ref, "revised_by": ref, ...content}`. `revised_by` names the revision whose content applies, and is absent when the act's own content applies. The content's members are those recorded in `@period`, with references in compact form: `at`, `record` and `cause`, and `timeliness`, `interpretation`, `matched_by`, `tied` and `since` where present; or `ambiguous` and `records`; or `limitation`, `records` and, for `interpretation_unavailable`, `interpretation`. `record` is one compact reference, or, where several records at one instant cause the transition, the list of them, ordered by item id, then context id, then source id, by Unicode code point (7.6.6). `policy` is not repeated in `begin` and `end`, since `end` is the baseline's. Each ambiguous candidate is a content in the same form, or `null`. Instants are as written in the record. In a participant perspective, and in an `expectation`, `expectations_about` or `what_remains` read that does not evaluate the expectation under its own interpretation, the periods are computed (7.6.14): `act` is `null`, `revised_by` is absent, and `policy_end`, where it is present by the rule above, is `null`, because computed periods apply the baseline endings (7.6.14).

**`open_work`.** A `<work>` is `{"expectation": ref, "outstanding": [p], "not_yet_due": [p], "withdrawn": [p], "fulfilled": [p], "overdue": [p], "ambiguous": [p], "candidates": {"<p>": [<standing>]}, "records": {"<p>": [refs]}}` (9.3.2). Property lists are sorted. `overdue` lists the outstanding properties whose overdue condition holds, and is omitted when empty. `ambiguous`, `candidates` and `records` are present only when a property's standing is `ambiguous`; each candidate is as in an ambiguous `<standing>`. An entry whose list depends on an ambiguous standing is placed in `ambiguous`. An entry that every combination of candidate standings places in the same list is placed in that list. An `<entry>` in `limitations` is `{"expectation": ref, "limitation": code, ...members}`. Entries in each list are ordered by the expectation's item, context and source id. With the attention filter, expectations that an ignore in effect at the cutoff targets are omitted from every list (9.5.5). An ignore is in effect from its effective time while the cutoff is at or before its `@until`, when it has one (9.5.6). An expectation that no ignore in effect targets, but that an ignore whose `@until` is unordered with the cutoff targets, is listed in `ambiguous` in place of `open` or `upcoming` (9.5.6). Under a non-baseline ending policy, placement follows open work rather than standing (9.3.2). An expectation with a property that the policy keeps open while it reads `fulfilled` or `withdrawn` is placed in `open`, with that property in its `fulfilled` or `withdrawn` list. A property whose period the policy has ended is not open work, whatever its standing: it places its expectation in no list, though it is listed under its standing when another property places the expectation.

**`changes`.** With frames, each side is the source's position in its own frame. `frame` is the resolved `to` frame, whose interpretation governs equality, and `from` is the resolved `from` frame. With Assertions, `from_assertion` and `to_assertion` are two of the source's statements about the subject, and the optional `frame` supplies perspective and interpretation; `from` is then absent. In a participant perspective, distribution coverage (4.4.2) is evaluated at that frame's cutoff. Each side is the source's position assembled from its statements that precede or are that Assertion in 5.2.1 order (7.1.1). Two issues published at the same instant are therefore separated by their ordinals (4.3.2). A statement unordered with a named Assertion makes the affected property ambiguous (4.5.3). When the `from` cutoff is after the `to` cutoff (4.2.5), or `from_assertion` follows `to_assertion` in 5.2.1 order, the read returns the limitation `reversed_comparison`. When the two cutoffs are unordered (4.2.5), it returns the limitation `unordered_comparison`. `interpretation` is the name of the interpretation that governs equality, or `null`: the frame's, or, where it names none, the one in force for the subject at the second side's time, which is the `to` cutoff or the `to_assertion`'s occurrence time (9.4.1).

`transitions` has one entry for each property `source_position` would list for the source and subject whose transition 5.6.2 reports, `unchanged` included, in property-name order. A `<transition>` is `{"property", "transition": "introduced" | "changed" | "cleared" | "withdrawn" | "reasserted" | "unchanged" | "ambiguous", "prior": ref | null, "new": ref | null, "withdrawn_by": ref, "prior_withdrawn_by": ref, "members": [{"member", "difference": "member_added" | "member_removed" | "member_changed"}], "candidates": [<classification>]}`. `prior` and `new` are the two sides' origins, and are `null` where that side has no value. `withdrawn_by` is present when the second side is withdrawn, and `prior_withdrawn_by` when the first is. `members` is always present. It is empty unless both sides are object values other than references; then it has one entry per top-level key that differs, in key order, and a difference inside a nested value is `member_changed` of its top-level key. `candidates` is present only for `ambiguous`: the first side's and the second side's classifications, in that order; `prior` and `new` are then `null` and `members` is empty. `matched_by` is present only on an `unchanged` entry whose two values are unequal literally and equal under an interpretation that a normalization put in force: the normalization's compact reference (5.5.4, 9.4.1).

**`conflicts`.** `conflicts` has one entry per property and per unordered pair of sources whose applicable values differ under the frame's interpretation. Three sources a, b and c with three different values give entries (a, b), (a, c) and (b, c). Entries are ordered by property, then by the pair's source ids, and sides are in source-id order. `expectation_conflicts` has one entry per property and per pair of expectations that are both in force and not yet fulfilled for the property at the cutoff and that require unequal values (7.1.5, 9.4.2). Entries are ordered by property, then by the pair's expectation references, and sides are in expectation-reference order. `ambiguous`, absent when empty, lists the pairs whose comparison at the cutoff depends on an unspecified order: `{"property", "sources": [id, id]}` for a pair of sources and `{"property", "expectations": [ref, ref]}` for a pair of expectations. `matched`, absent when empty, lists in the same forms, ordered by property and then by the pair, the pairs whose values are unequal literally and equal under an interpretation that a normalization put in force, each with `matched_by`, the normalization's compact reference (9.4.2). They are not conflicts. `interpretation` is the frame's, or, where it names none, the one in force for the subject at the cutoff (9.4.2).

Under a frame that names no interpretation, a pair of expectations is compared under each expectation's own interpretation at the cutoff (7.2.4, 9.4.2). The pair is in `expectation_conflicts` when its values are unequal under both, in `ambiguous` when they are equal under one and unequal under the other, and in neither when they are equal under both; it is then in `matched` where a normalization put one of those interpretations in force and the values are unequal literally. An expectation pair's entry in any of these lists carries `interpretations`, the two sides' interpretation names (`null` for literal comparison) in side order, when either differs from the read's `interpretation`; it is absent otherwise.

**`story`.**

- `<interval>` is `{"start": instant, "end": instant | null}`, with `end` `null` until the story has ended at the cutoff. A story whose sides never disagreed under its interpretation (7.2.6), and a change story with no period (7.6.12), has the empty interval `{"start": null, "end": null, "empty": true}`.
- `<ending>` is `{"kind": "alignment" | "withdrawal" | "fulfillment" | "correction" | "normalization" | "interpretation" | "review" | "reconstructed" | <a policy's cause>, "record": ref | [refs], "at": instant | null, "matched_by": ref}`. Under a non-baseline ending policy, `kind` is the cause that the policy's end act names (7.6.5). `record` is a list where several records at one instant cause the ending, in the order of 7.6.6. `"at_is_provenance": true` marks an `at` that is a correction's own time, which is not an ending time (7.2.6). `matched_by`, present only on an `alignment` or `fulfillment` ending whose record matches only under an interpretation that a normalization put in force, is that normalization (7.6.5). A story that a normalization ends while open ends by `normalization`, with the normalization as its record and, as `at`, the instant from which its interpretation is in force for the subject: its effective time, or the later instant at which the subject came under it (7.3.8). A change story whose last review is withdrawn while the interpretation in force leaves its revision changing nothing has, from the withdrawal's effective time, a period of no length that ends by `normalization`, with the normalization that put that interpretation in force as its record and that time as `at` (7.6.2); before that time its ending is the review. A story with no period ends by `reconstructed`, `correction`, `normalization` or `interpretation`, chosen in that order where more than one applies, with `at` `null` (`at_is_provenance` aside): `reconstructed` with the backfilled Assertion as record (7.3.7), `correction` with the correction, `normalization` with the normalization in force when its sides first differ literally, or, for a change story, at its revision, and `interpretation`, for two expectations whose contexts' interpretations alone make the sides equal, with the two expectations as record (7.6.12). A `normalization` ending of a story with no period applies from the `since` of its end act, the instant at which its sides first differ literally or the change story's revision occurred: at a cutoff before `since`, `ending` and `baseline_ending` are `null` and `standing.open` reads `not_started` (7.6.12, 7.6.14).
- `<story standing>` is `{"open": "open" | "ended" | "continued_in" | "not_started" | "ambiguous", "continued_in": id, "review": "unreviewed" | "reviewed" | "ambiguous", "disagreement": "disagreeing" | "aligned" | "absent" | "ambiguous" | <limitation>, "matched_by": ref, "attention": "attended" | "ignored" | "ambiguous"}`. `disagreement` is the object `{"limitation": "interpretation_unavailable", "interpretation"}` where the story's interpretation at the cutoff is unavailable (*Unavailable interpretations*). `matched_by` is present only when `disagreement` reads `aligned` because the sides are equal only under an interpretation that a normalization put in force: that normalization (9.5.2). `continued_in` names the representative, and is present only for a story that a `continuous` reconciliation continues in another (7.3.4). `not_started` applies at a cutoff before the story's interval begins, or, for a story with no period, before the `since` of a `normalization` ending, including in a participant perspective whose account does not yet show the disagreement (7.2.4, 7.6.12, 4.6.1). Any dimension reads `ambiguous` when it depends on an unspecified order (9.5.2). At the instant of a review tied with a revision (7.3.6), the related story's `open` reads `ambiguous` and the reviewed story's standing is unaffected. `disagreement` is absent for change stories. `attention` is present only when `args.attention_filter` is set; it reads `ambiguous` when the cutoff and an ignore's `@until` are unordered (9.5.6).
- A story that `open_stories` lists as superseded keeps its own standing here.
- `ending` is the story's ending under its ending policies and `baseline_ending` its ending under the baseline (7.7.4). Each is read from the matching end act of the story's latest period that began at or before the cutoff (7.6.14), and is `null` when that period has not ended at or before the cutoff under those policies. For `ending`, that is the end act of the policy governing the unit when the period ends, with `at` as `policy_end` gives it (*Periods*, 7.7.3). A story with no period (7.6.12) has, as both, the ending its baseline end act gives, whatever its policy: at every cutoff, or, where that end act carries `since`, at every cutoff that `since` is at or before. Under the baseline the two are equal. A story that reads `continued_in` reads `not_started` at a cutoff before its representative's period begins (7.6.14). `standing.open` follows `ending`. `interval` is the event-time interval of 7.2.4, which ends at the baseline ending.
- `policy` is the story's ending policy at the cutoff (7.7.2), `null` for the baseline, or the ambiguous form of §5 *Ending policies* where tied `adopt_policy` acts leave it ambiguous. `interpretation` is the name of the story's interpretation at the cutoff, `null` for literal comparison, and `normalization` the compact reference of the normalization that put it in force, `null` when none applies, or `{"ambiguous": [refs]}` with `interpretation` `null` where the interpretation in force is ambiguous (7.2.4, 7.3.8). For a conflict story between two expectations whose own interpretations differ at the cutoff (7.2.4), `interpretation` is the list of the two sides' names (`null` for literal comparison), in side order, and `normalization` concerns the sides compared under the interpretation in force. `periods` lists the story's periods (*Periods*, above). It is `[]` for a story with no period (7.6.12) and for a story that reads `continued_in` (7.6.11).
- `related` lists the story's related stories in both directions (9.5.1), sorted. `match_under_read_interpretation` is present only when the read's interpretation differs from the story's at the cutoff: the frame names an interpretation other than the story's. It is the limitation object above where the read's interpretation is unavailable.
- A change story also carries `transitions`: `[{"property", "transition", "prior": ref | null, "new": ref}]`, computed in the corrected account, with unchanged properties not listed. Its length is the transition count (7.2.3). It also carries `transitions_from`: the latest `reconstructed` reconciliation that targets the story, or else its detection (7.3.7). When a correction now targets a prior or new Assertion of those transitions, it carries `transition_corrections`: `[{"record": ref, "corrections": [refs]}]`, one entry for each such Assertion (7.2.7). It is absent otherwise.

**`open_stories` and `pending_review`.** Every list is sorted by id.

- `open_stories.stories` lists the stories in scope whose `open` dimension reads `open`, except superseded ones and ones tied for latest (9.5.3). A family's disagreement is counted once. When several stories of one family (7.2.2) read `open` at the cutoff, only the one whose interval began latest is listed in `stories`, and the others are listed in `superseded`. When the latest interval starts are equal or unordered (4.2.5), no story is chosen: the stories that no other story of the family began after are listed in `ambiguous`, and the others in `superseded`. A story that reads `continued_in` is not listed, since its representative is. Change stories belong to no family and are never superseded.
- `ambiguous` lists the stories whose `open` dimension reads `ambiguous` and the stories tied for latest in a family; `limitations` lists those whose read is a limitation. Stories that read `not_started` or `ended` are not listed. `count` is the length of `stories`. Neither `superseded`, `ambiguous` nor `limitations` is counted.
- `pending_review.stories` lists the stories in `open_stories.stories` whose `review` dimension reads `unreviewed`, and `pending_review.superseded` lists the stories in `open_stories.superseded` that read `unreviewed` (9.5.4). Its `ambiguous` lists the stories `open_stories` lists as ambiguous, together with the stories in `open_stories.stories` whose `review` dimension reads `ambiguous`. Its `limitations` are those of `open_stories`.
- With the attention filter, superseding is decided first. A story whose `attention` reads `ignored` is then omitted from `stories` and `count`, and one whose `attention` reads `ambiguous` is listed under `ambiguous` in its place. `superseded` and `limitations` are not filtered.

**`what_remains`.** The units of work in scope that are open at the cutoff under their ending policies (9.5.7). A `<remains>` is `{"kind": "conflict" | "change" | "expectation", "unit": id | ref, "began": <transition>, "policy": null | {"name", "version"} | {"ambiguous", "records"}, "standing": {...}, "parents": [{"story": id, "open": <open dimension>}], "succeeds": [ids], "children": [refs], "interpretation": name | null | [name | null, name | null]}`.

- `unit` is the story id, or, for an expectation property, the expectation's compact reference with the property selector (`"door-101|e-lacquer|a-601#finish"`).
- `began` is the begin act of the unit's current period: the latest open period that began at or before the cutoff (*Periods*).
- `standing` is, for an expectation property, `{"standing": <its 6.6.1 standing>, "overdue": bool}`, with `overdue` present when it is `outstanding` or `not_yet_due`. For a story it is `{"review": ..., "disagreement": ...}`, as in `<story standing>`, with `disagreement` absent for a change story. Both carry `attention` when `args.attention_filter` is set.
- `parents` lists, sorted by story id, the stories the current period of an expectation property is nested under (7.6.15), each with its `open` dimension at the cutoff, which may be `"ended"`. It is `[]` for a story.
- `succeeds` lists, sorted, the stories that a story's detections' `@relates_to` reference; they are never parents. It is `[]` for an expectation property.
- `children` lists, sorted, the units of the open expectation properties whose current period a story is a parent of, upcoming ones included. It is `[]` for an expectation property.
- `interpretation` is the name of the interpretation the entry was evaluated under at the cutoff, or `null`: the unit's own interpretation (7.2.4, 7.6.13) when the read evaluates it under its own, which a frame naming none always does, otherwise the interpretation the read computed it under (7.6.14). For a conflict story between two expectations whose own interpretations differ, it is the list of the two names, as in `story`. `policy` is the policy governing the unit at the cutoff (7.7.2), or the ambiguous form of §5 *Ending policies*.
- A story's `standing.disagreement` may be the `interpretation_unavailable` limitation object, and may carry `matched_by`, as in `<story standing>`; the entry keeps its list.

Lists and counts:

- `open` lists every open unit except those listed elsewhere. `upcoming` lists the expectation properties that read `not_yet_due`. Conflict stories are listed and superseded exactly as `open_stories` lists them: a family's other open stories go to `superseded`, stories tied for latest go to `ambiguous`, and a story that reads `continued_in` is not listed.
- `ambiguous` lists the entries whose list depends on an ambiguous standing: an `open` dimension that reads `ambiguous`, a family tie, or a property standing whose candidates would place the entry in different lists, as in `open_work`. `limitations` lists `{"kind", "unit", "limitation": code, ...members}` for each unit whose result is a limitation.
- `counts` gives, for each kind, the number of entries in `open`; every kind is present, with `0` when there are none. `upcoming`, `superseded`, `ambiguous` and `limitations` are not counted.
- Each list is ordered by kind (`conflict`, `change`, then `expectation`), then by `unit`.
- With the attention filter, superseding is decided first. An entry whose `attention` reads `ignored` is then omitted from `open`, `upcoming` and `counts`, and one whose `attention` reads `ambiguous` is listed under `ambiguous` in its place. `superseded` and `limitations` are not filtered, and neither are `parents` and `children`.

**`transition_check`.** The audit of 9.5.8, always in the record perspective: the resolved frame reports `"record"` and interpretation `null`, without `normalization`, and the cutoff serves only to decide the scope's members. A `<difference>` is `{"unit": id | ref, "transition": "begin" | "end", "difference": "missing" | "extra" | "different", "act": ref | null, "policy": null | {"name", "version"}, "recorded": <content>, "derived": <content>}`. `unit` is as in `what_remains`. `act` is the recorded act, `null` for `missing`. `policy` is `null` for a baseline transition, or names the policy of a compared policy end act. `recorded` is the act's applicable content and is absent for `missing`; `derived` is the derived content and is absent for `extra`. Contents are in the form of a `<transition>` without `act` and `revised_by`, or `null`. Differences are ordered by `unit`, then by `act`, with `missing` entries after the others for their unit, in the order of the derived transitions. `unverified` lists, sorted, the end acts that name a policy the reference does not implement and that policy governs the unit when the act's period ends, or is a candidate to govern it there (7.7.2, 7.7.3), and the begin and end acts of a unit evaluated under an unavailable interpretation (§5, *Unavailable interpretations*), whose transitions are not compared (9.5.8). The fixture policy (§5) is implemented, so its end acts are compared with its own derivation, not listed as unverified, for every period whose ending it governs or is a candidate to govern. End acts naming a policy that does not govern their period's ending are neither compared nor listed (9.5.8). Acts whose applicable content is `null` are never `extra`.

**`distribution`.** A `<distribution>` is `{"record": ref, "at": instant, "issuance": id | null, "recipients": [ids]}`. `distributions` lists the dated distributions about `item` whose occurrence is at or before the cutoff, in presentation order. `ambiguous`, absent when empty, lists those whose relation to the cutoff is unspecified (4.5.3). In a participant perspective, only the distribution records covered for the participant (4.4.2) are listed. `recipients` are the ids in the record's `@distribution`, in recorded order. `issuance` is the context id of the issuance distributed. That is the `@issuance` of a later distribution of a communication; the milestone, for a publication or a later distribution of it; or the record's own context, for a self-description. It is `null` only for a distribution record about a communication that names no `@issuance`.

**`distributed_to`.** `records` lists, in presentation order, every statement about an Item in scope that was distributed to the participant by the cutoff (4.4.2, 9.7.1). These include the self-descriptions, publications and later distributions that list the participant. The publications and communications distributed to the participant are the subjects of those records.

**`adjacency`.** `outgoing` and `incoming` are sorted and use the Connections active at the cutoff. With `history`, `"history": {"<from->to>": [{"state": "active" | "inactive", "from": instant, "to": instant | null}]}` has an entry for every Connection touching the Item that was created at or before the cutoff, active or not. Segments end at the cutoff: the last segment's `to` is `null`. `"history_ignored_acts": {"<from->to>": [refs]}` lists the lifecycle acts at or before the cutoff that changed nothing (8.6.6). It has a key only for Connections that have such acts, and is absent when none has.

**Declared extension (fixtures only).** Under 10.4.4 the reference declares one extension: the member `@x-fixture-refs`, whose value is a list of Item id strings. That is a reference form other than 2.4.1–2.4.2. A record carrying it has downstream impact by definition (8.5.2(e)), so `plan_removal` of it is refused with `"extension": "@x-fixture-refs"` (§2). While any record carries it, `plan_removal` of any Item is refused in the same way, because dependency knowledge is incomplete (10.3, 10.4.4). Reads otherwise treat it as any extension member (10.4.2). The extension is listed with the reference's conformance claim (10.5.3).

## 6. Error codes

| Code | Meaning |
|---|---|
| `occupied` | A changed write to an occupied triple, or creation of an existing Item id with different content (8.1.3, 8.1.5; 10.2.1). |
| `10.2.2` … `10.2.9` | The validation rule that rejected the write. |
| `duplicate_key` | An object with a duplicate key, in `values_json` or `definition_json` (5.1.1; reported under 10.2.4). |
| `number_out_of_range` | A number outside 5.1.2 (10.2.4). |
| `plan_stale` | A confirm after the target, or any record the impact test examined, changed since the plan (8.5.4). |
| `plan_unknown` | A confirm or cancel of a plan that this session did not issue, or has already confirmed or cancelled (8.5.4). |

Values are written as JSON text, so duplicate keys and out-of-range numbers can be tested. A step's `values` may instead be given as `"values_json": "<raw JSON text>"`, and an `item` step's `definition` as `"definition_json"`. Text that is not valid JSON, or that is not a JSON object, fails `10.2.4`.

When one defect in a write matches more than one validation rule, the code is:

1. for an instant that is present but not in a 4.2.1 form, wherever it appears: `10.2.4`;
2. for a missing context role or required context member, or a required member of the wrong type other than an instant (for example a non-integer ordinal): `10.2.3`, or `10.2.5` inside a corrected Item;
3. for a `@targets`, `@basis`, `@establishes` or `@reaffirms` that is not a list of references, or an `@after`, `@relates_to`, `@successor`, `@representative` or `@issuance` that is not a single reference: `10.2.2`;
4. for a reference object not in a form of 2.4.1–2.4.3 (for example an Assertion reference missing a coordinate, or an undefined `@ref` kind): `10.2.4`. A well-formed reference that does not resolve is `10.2.2`;
5. for `@effective` on an act that 8.4.1 does not allow it on: `10.2.7`; on a record that is not an act: `10.2.4`;
6. for a begin act, an end act, a `revise` or an `adopt_policy`, any defect that 10.2.9 names, including a `@period` of the wrong form or with a cause its unit does not allow: `10.2.9`, unless items 1 to 5 apply. A `@period` on any other record is `10.2.4`; a withdrawal that targets a begin or end act or a reconciliation is `10.2.6`; a correction that targets a begin or end act or a `revise` is `10.2.9`;
7. for an `interpretation` or `policy` of the wrong shape in an expectation context's `@context`: `10.2.3`; for `policy` or `policy_version` of the wrong shape in a detection's or reconciliation's `@frame`, or on a review's `@frame`: `10.2.4`;
8. for a normalization (`"@action": "reinterpret"`): a `@targets` that is a list of references but not exactly one Item reference is `10.2.6`; an `@interpretation` that is missing, or that is neither `null` nor `{"name": <string>, "version": <string>}`, is `10.2.4`; a well-formed `@interpretation` naming an interpretation the reference does not have (§5, *Interpretations*), on a normalization or in the `@corrected` values of a `replace` correction, is `10.2.9`. A reconciliation with `"@outcome": "reinterpret"` is an undefined value of a defined member and fails `10.2.4` (10.4.1). `@effective` is allowed on a normalization and on an `adopt_policy` (8.4.1).

Any other defined member placed where 2.4.4 does not allow it, or with the wrong shape, is `10.2.4`. Fixtures give each rejected write exactly one defect. A write with several defects may fail with the code of any of them.

## 7. Automatic maintenance (spec 7.2.8, 7.6.9)

When a write changes a side of a recorded conflict story, or the transitions of a recorded change story, the implementation records in the same operation the continuation detection, related story or reconciliation that the spec requires. Continuations and related stories attach to the family's latest story that is not `continued_in` another; after a join (7.3.4), that is the representative. Maintenance records a continuation only for evidence that the write brought into an unreviewed story (7.2.5). A correction that changes a change story's transitions generates no record; reads recompute the transitions (7.2.7). Generated records use deterministic names, so that fixtures can refer to them:

- **Generated detection.** Context `"<story>/d<n>"`. Source: the story itself. `n` counts the story's detections from 1.
- **Generated related story.** Item `"<prior story>+<n>"`, with its detection at `"<prior story>+<n>/d1"`. `n` counts related stories generated from that prior story.
- **Generated reconciliation.** Item `"<target story>/r<n>"`, with context `"<target story>/r<n>/at"` and the reconciliation itself as source.

Every generated record is self-sourced. Its context is an `event` Item, `{"@context": {"role": "event", "at": <instant>}}`, whose `at` is the occurrence time of the triggering record. When publication instants compete (4.4.1), it is the later one. Generated Items have no label and an empty definition. A related story has the prior story Item's kind, and a reconciliation has kind `reconciliation`. Every generated `@frame` is `{"scope": <the first detection's scope>, "cutoff": <the context's at>, "perspective": "record", "interpretation", "interpretation_version"}`, with the interpretation in force for the story's subject at the context's `at` (7.2.4, 7.3.8), `null` and `null` for literal comparison. Where that interpretation is ambiguous, `interpretation` and `interpretation_version` are `null` and the frame also carries `"normalization": {"ambiguous": [refs]}`, listing full references to the normalizations concerned, ordered as in 7.6.6 (5.5.5). The key is absent otherwise. A generated frame for a conflict story between two expectations records the interpretation in force in the same way, since maintenance compares as a frame naming none does, which compares two expectations under their own interpretations (7.2.4). When the policy governing the story at the context's `at` is not the baseline, it also carries `policy` and `policy_version`, naming that policy (7.7.2); under the baseline they are absent. Where a generated record cites a story's detection, in `@relates_to` or `@targets`, it cites the story's first detection; any detection identifies the story (7.3.1).

- A continuation's values are `@action: "detect"`, the first detection's `@story`, `@basis` (the sides' applicable Assertions, each with the family's `property` selector) and `@frame`.
- A related story's detection has the same members, with the prior story's `@story`, and adds `@relates_to`: the prior story's first detection.
- A related change story of 7.3.8, which maintenance records when a normalization or a Connection operation makes a revision a change again, is named as a related story, `<prior story>+<n>`, where the prior story is the latest change story recorded for the revision, the one whose ending is the normalization. Its detection carries `@story` `{"kind": "change", "subject"}`, `@transitions` (the revision's transitions under the interpretation in force from the instant it begins), `@basis` (their prior Assertions and the revised Assertion), `@frame` and `@relates_to`. Its context's `at` is the occurrence time of the triggering record, the normalization or the Connection operation, while its period begins at the instant from which the revision changes a property again.
- A reconciliation's values are `@action: "reconcile"`, `@targets`, `@outcome`, `@basis` and `@frame`:
  - `continuous`: `<target story>` is the representative, the story whose interval begins earliest (7.3.4). `@targets` are the joined stories' first detections, in story-id order. `@basis` is the triggering record, and `@representative` names the representative.
  - `split`: `@targets` is the split story's first detection, and `@basis` is the record that ended its first episode. `@successor` names the new story `<target story>+<n>`, whose detection is generated in the same operation.
  - `boundary`: `@targets` is the reviewed story's first detection, and `@basis` is the triggering record. This includes backfilled evidence showing that the sides aligned before the review: no story is opened (7.3.5).
  - `reconstructed`: `<target story>` is the change story. `@targets` is its first detection, `@basis` is the backfilled issuance's Assertion, and `@transitions` lists the reconstructed transitions (7.3.7). It is `[]` when the revision now changes no property; the change story then has no period (7.6.12). The related change story `<target story>+<n>` is generated in the same operation. Where several change stories are recorded for the targeted revision (7.3.8), a `reconstructed` reconciliation is generated for each of them, in the order they were recorded, each with that story's reconstructed transitions, and the one related change story is generated from the latest of them (7.3.7). Its detection carries `@story` `{"kind": "change", "subject"}`, the backfilled revision's `@transitions`, `@basis` (their prior Assertions and the backfilled Assertion), `@frame` and `@relates_to`.

Fixtures may also write these records explicitly. A write that would duplicate what maintenance generated is an identical replay, provided the content matches.

### Recorded transitions (spec 7.6, 7.7)

In the same operation as the write that requires them, after the story maintenance above, the implementation records the begin and end acts of every affected unit of work and revises those whose applicable content changed (7.6.9, 7.6.10). For units governed by the fixture policy (§5) it records and revises that policy's end acts too. The `assert` result lists these records in `transition_acts` (§2), in the order recorded. Units come in order, stories by id and then expectation properties by the expectation's compact reference and the property name. Within a unit, the revisions come first, in the order of the acts they revise, and then the new acts in period order: each period's begin act, then its baseline end act, then its end act under the fixture policy.

Names:

- **Story begin act.** `(<story>, "<story>/b<n>", <story>)`. `n` counts the story's begin acts from 1.
- **Story end act.** `(<story>, "<story>/e<n>", <story>)`. `n` counts the story's end acts from 1, baseline and policy alike, in the order recorded.
- **Story revision.** Item `"<story>/v<n>"`, with context `"<story>/v<n>/at"` and the revision itself as source. `n` counts the revisions recorded for the story's begin and end acts from 1. These names are separate from the `/r<n>` names of the reconciliations above, whose numbering does not change.
- **Story-held expectation property acts.** An expectation property whose first period, as derived when its first act is recorded, has exactly one parent story (7.6.7, 7.6.15) has every act recorded on that story, whatever later backfill or corrections show. Where it is then ambiguous whether the first period has exactly one parent, or its beginning is a limitation, the property's acts are named as below for other properties. Story-held acts are named `(<story>, "<story>/exp:<path>/b<n>", <story>)` for a begin act, `(<story>, "<story>/exp:<path>/e<n>", <story>)` for an end act and `(<story>, "<story>/exp:<path>/v<n>", <story>)` for a revision, with `<path>` and the numbering as below. The `/exp:` segment keeps these contexts apart from the story's own `/d`, `/b`, `/e`, `/v` and `/r` names. For example, the first begin act of `door-101|e-lacquer|a-601#finish`, established by the review of `story-1`, is `story-1|story-1/exp:door-101/e-lacquer/a-601/finish/b1|story-1`.
- **Expectation property acts.** Any other expectation property's acts are each their own Item, with context `"<Item>/at"` and the Item itself as source: `"exp:<path>/b<n>"` for a begin act, `"exp:<path>/e<n>"` for an end act and `"exp:<path>/v<n>"` for a revision, numbered per unit as for a story. `<path>` is `"<item>/<context>/<source>/<property>"`, built from the expectation's triple and the property name. In each of those four parts, `%` is written `%25`, `/` is written `%2F`, `|` is written `%7C`, `#` is written `%23`, `^` is written `%5E` and `>` is written `%3E`, so that a name is unambiguous and never contains `|`, `#`, `^` or `->`. For example, the first begin act of `door-101|e-lacquer|a-601#finish` is the Item `exp:door-101/e-lacquer/a-601/finish/b1`, at context `exp:door-101/e-lacquer/a-601/finish/b1/at`.

Contexts are `event` Items, as for the generated records above. Their `at` is the occurrence time of the triggering record, the later one when publication instants compete. The triggering record is the write that required the act: the statement, act, correction, publication, normalization or Connection operation written (for a Connection, its `at` or its act's occurrence time), or, when a story is recorded by a detection, that detection. A revision of an act that already has a revision is ordered after it (7.6.10): when the triggering time is not after the `at` of the act's latest revision (4.2.5), the new revision's context takes that revision's `at`, and the new revision carries `@after` referencing it. Generated Items have no label and an empty definition. An expectation property's act Items have kind `begin` or `end`, and revision Items kind `reconciliation`. Story-held acts create only their context Items.

Values:

- A begin act: `@action: "begin"`, `@targets` and `@period`. A story's begin act targets the story Item, `{"@ref": "item", "id": <story>}`, not a detection. An expectation property's begin act targets the expectation with the property selector.
- An end act: `@action: "end"`, `@targets` (its begin act) and `@period`, whose `policy` is `null`, or `{"name": "fixture-change-closes-with-directive", "version": "1"}` under the fixture policy.
- A revision: `@action: "reconcile"`, `@targets` (the act it revises), `@outcome: "revise"`, `@period` (the revised content, or `null`) and `@basis` (the triggering record). It carries no `@frame`, and `@after` only as above.
- A `@period` carries exactly the members that 7.6.4 to 7.6.6 give it, with full reference objects in `record`, `records` and `tied`.

Fixtures may write begin acts, end acts and revisions explicitly. An identical write of a generated one is a replay; any other explicit write of a baseline act, or of a revision of one, fails `10.2.9`, unless the unit is evaluated under an unavailable interpretation (§5, *Unavailable interpretations*), when it is not compared with the derivation (10.2.9, 7.6.14). An explicit end act naming the fixture policy, or a revision of one, is compared with the reference's own derivation of that policy, and one that differs fails `10.2.9` on that ground alone, whether or not its content also gives an ignore as a `record` (7.7.5, 10.2.9). End acts naming a policy the reference does not implement are written explicitly and are checked only for their shape, their target, and that their content gives no ignore as a `record` (7.7.4, 7.7.5).

**Normalizations.** A normalization's write records, in the same operation, the begin and end acts and revisions of every unit in its scope that it changes (7.3.8): units whose subject is a member of its scope at or after its effective time. The `assert` result lists them in `transition_acts` in the order above; `generated` lists any related story or other story record that maintenance records because of it, including a related change story for a revision that it makes a change again (named as stated at the start of this section; 7.3.8). A Connection operation that changes which normalizations apply to a subject is maintained in the same way, and its write result lists what it records, as §2 states for `connect`.

## 8. Transition check after every fixture (spec 9.5.8, I-17)

After a fixture's steps have all passed, the runner runs `transition_check` with frame `{}`: every Item in the store, cutoff `"now"`, record perspective. If its `differences` list is not empty, the fixture's status is `FAIL`, and its detail begins with `transition_check:` followed by the differences. `unverified` entries never fail a fixture. A fixture that carries `"transition_check": false`, with a `note` quoting the rule that makes the check inapplicable to it (§1), is not checked. A BLOCKED fixture is not run, and a fixture whose steps fail is reported from its steps.
